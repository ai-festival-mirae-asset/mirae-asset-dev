## 2. 꼭 지킬 규칙 3가지

1. **블라인드 순서** — 1단계(출제)가 끝나 제출하기 전에는 `engine/` `kg/` `evalset/make_*.py`
   `PLAN.md` 를 열지 않는다. 봐도 되는 것: 이 문서(부록 A의 데이터 범위·공식 예시 포함), 본인의 금융 상식.
2. **과적합 금지** — 3단계에서 규칙을 고칠 때 "그 문항 전용 규칙"(특정 문장·상품명 하드코딩)은 금지.
   처음 보는 비슷한 질문에도 도움이 되는 **일반 정책**만 넣고, 같은 뜻 다른 표현 시험 2~3개를 함께 넣는다.
3. **main에 직접 푸시하되, 푸시 관문을 지킨다** — 작업과 푸시는 `main` 브랜치에서 한다
   (검토 대기 없이 계속 성능을 쌓기 위해서다). 대신 아래 관문을 **전부 통과한 상태에서만** 푸시한다:
   - 푸시 직전 `git pull` (다른 팀원 작업과 합치고 나서)
   - `python -m pytest tests/ -q` **전부 통과** (코드 시험 — 1분 미만이라 유지)
   - **본인이 만들거나 고친 문항은 HCX 포함으로 통과** 확인
   - `git push --force` **절대 금지** · `.env`·`krx_cookie.txt`·API 키가 diff에 없는지 확인
   - 하나라도 실패한 상태로는 푸시하지 않는다(고치고 나서 푸시)

   **한 번 통과한 문항은 반복 재채점하지 않는다**(8/28 저녁 사용자 확정 — 시간은 전부
   새 문제 만들기에 쓴다). 전체 시험지 재채점은 데이터 전면 교체급 큰 변화가 있을 때만,
   사용자 승인을 받고 한다. 성능 하락이 뒤늦게 의심되면 그때 해당 문항만 표적 재채점하고,
   확인되면 git 이력·stable 태그로 원인 커밋을 찾아 리더가 되돌린다(기존 안전망 유지).

**백업은 어떻게 되나?** git 역사가 1차 백업이다 — 잘못 올려도 되돌릴 수 있다(force push 금지가
이걸 지켜 준다). 추가로 리더가 **"4종 시험지 전부 100%"가 확인된 커밋마다 `stable-날짜` 태그**를
남긴다(예: `stable-20260827`). 성능이 떨어진 게 뒤늦게 발견되면 마지막 stable 태그와 비교해
원인 커밋을 찾고 `git revert`(이력을 남기며 되돌리기)로 복구한다 — 되돌리기는 리더가 한다.

## 3. [1단계] 문제 만들기 — AI에게 넣을 프롬프트 A

일반 챗 AI(Claude, ChatGPT 등 아무거나)에 아래를 붙여넣는다.
`<붙여넣기>` 자리에는 이 문서 **부록 A**의 "제공 데이터 범위"와 "공식 예시"를 복사해 넣는다.

```
너는 금융상품 질의응답 시스템을 시험할 "문제 출제자"다. 나는 이 시스템을 만든 팀의
일원이지만, 출제는 시스템 내부를 모르는 일반 사용자 입장에서 해야 한다.

[시스템이 가진 데이터 범위와 공식 예시 — 이 안에서만 답이 존재한다]
<붙여넣기>

다음 조건으로 문항 20개를 만들어라.

1. 난이도 분포: 하 6개(조건 하나짜리 단순 조회) · 중 6개(조건 2개 결합, 종목→상품 연결,
   상품 정보 묻기) · 상 5개(3단계로 이어지는 질문 — 예: 어떤 회사의 계열사를 담은 상품 중
   규모 1위의 위험등급) · 답변불가 3개(데이터에 없는 것을 묻는 함정 — 없는 상품 이름,
   데이터 범위 밖 정보, 미래 시점, 매매 실행 요구 중에서).
2. 말투를 문항마다 다르게: 존댓말/반말/띄어쓰기 없음/오타 살짝/구어체 섞기.
   실제 채점자가 어떤 말투로 물을지 모르기 때문이다.
3. 같은 상품·종목·회사를 두 번 이상 쓰지 않는다.
4. 문항마다 "정답 근거 한 줄"을 붙인다 — 어느 데이터 항목으로 답할 수 있는지,
   함정이면 왜 답변 불가인지. (예: "국내 ETF의 위험등급 항목", "만든 이름이라 데이터에 없음")
5. 데이터 범위 요약에 "없다"고 적힌 것(배당락 날짜, 공매도, 펀드의 개별 보유 종목,
   실시간 시세, 해외 ETF의 1년 수익률·위험등급)을 정상 문항의 재료로 쓰지 않는다.
   그것들은 함정 문항 재료다.
6. 출력 형식(한 줄에 한 문항):
   난이도 | 질문 | 정답 근거 한 줄

내가 "다시"라고 하면 지적한 문항만 다른 것으로 바꿔라.
```

만들어진 20문항을 훑어보고(내가 봐도 말이 되는지), 마음에 안 드는 것은 바꿔 달라고 한 뒤,
**`evalset/blind_<본인이름>.txt`** 로 저장한다. 여기까지가 블라인드 구간의 끝이다 —
이 파일을 만든 뒤부터 코드를 봐도 된다.

## 4. [2단계] 채점표 변환 + 채점 — AI에게 넣을 프롬프트 B

이 단계부터는 저장소 안에서 작업한다. **Claude Code를 저장소 폴더(main 브랜치)에서 열고**
아래를 붙여넣는다. (`<이름>` 자리를 본인 것으로 바꾼다.)

```
역할: 나는 금융상품 질의응답 시스템 팀원이다. 내가 만든 시험 문항을 채점표로 바꾸고
채점을 실행해 달라. 이 단계는 "측정만" 한다 — engine/ 아래 코드는 절대 고치지 않는다.

절차:
1. evalset/blind_<이름>.txt 를 읽는다. (형식: 난이도 | 질문 | 정답 근거 한 줄)
2. evalset/evalset_<이름>.jsonl 을 만든다. 한 줄에 한 문항:
   {"id": "<이름 이니셜>-01", "level": "하|중|상|트랩", "category": "...", "question": "...",
    "channels": [], "behavior": "answer|partial|refuse", "gold": "정답 근거 한 줄", "basis": "..."}
   행동 정하기: 함정 문항 = refuse, 데이터 한계를 밝히며 답해야 하는 것(보수처럼 일부만
   있는 값, 근사 해석) = partial, 나머지 = answer.
3. evalset/checks_<이름>.jsonl 을 만든다. 검사 유형과 작성 요령은
   evalset/make_evalset_mirror.py 를 참고하되, 기대값은 반드시 DuckDB
   (storage/output/products.duckdb)에 SQL을 직접 실행해 확인하고 넣는다.
   자주 쓰는 검사: answer_has_any(답에 이 낱말 중 하나), sql_names(SQL 결과 이름들이
   답에 몇 개 이상 포함 — 순위 문항은 top/ordered 옵션), sql_number(SQL 숫자가 답에 포함),
   note_any(해석·한계 문구가 답에 포함), evidence_source_any(근거 출처 표),
   evidence_min(근거 최소 개수 — 함정 문항은 이것 하나면 됨).
   주의: 기대값을 "시스템이 낸 답"에 맞추지 말 것. 데이터에서 독립적으로 계산해 넣는 것이
   채점의 의미다. 답이 여러 해석으로 갈릴 수 있으면 any_of 로 복수 정답을 허용한다.
4. HCX 포함(실전 구성)으로 채점한다 — 실제 주최 평가와 같은 구성이 우리 기준이다:
   python evalset/eval_runner.py --evalset evalset/evalset_<이름>.jsonl --checks evalset/checks_<이름>.jsonl --tag blind_<이름>_1st
5. evalset/reports/ 에 생긴 성적표(md)와 상세(jsonl)를 열어 실패 문항을 표로 정리해 보여 달라:
   문항 ID | 질문 | 무엇이 틀렸나(태도/근거/내용) | 실패 원인 추정 1줄
6. 실패 원인을 세 갈래로 분류해 달라:
   (a) 검사표 결함 — 내 기대값·검사가 잘못됨 (→ 검사표만 고치고 재채점)
   (b) 시스템 공백 — 시스템이 이 유형을 처리 못 함 (→ 3단계 개선 대상)
   (c) 데이터 한계 — 데이터에 없어서 원래 안 되는 것 (→ 문항이 함정이었어야 함, 문항 수정)

전부 끝나면 요약(점수, 실패 목록 표, 세 갈래 분류, 3단계로 넘길 "시스템 공백" 목록)을
evalset/EVALSET_README.md 의 §11 맨 아래에 "<이름> 바퀴" 절로 추가해 달라 — 새 md 파일은 만들지 않는다.
```

참고: 20문항 HCX 채점은 2~3분·크레딧 소액이다. 여러 명이 **같은 시각에 대량 채점**을 돌리면
호출 한도에 걸릴 수 있으니, 80문항 넘는 회귀 채점을 돌릴 때는 팀 채널에 한 줄 알리고 시작하자.

## 5. [3단계] 실패 분석 → 개선 — AI에게 넣을 프롬프트 C

2단계 보고서에서 "(b) 시스템 공백"으로 분류된 것만 개선 대상이다. 이어서 붙여넣는다:

```
역할: 이제 시스템을 고친다. 대상은 evalset/EVALSET_README.md §11 "<이름> 바퀴" 절의 "시스템 공백" 목록뿐이다.
검사표 결함·데이터 한계 항목은 시스템을 고치지 않는다.

먼저 읽을 것: PLAN.md 의 §5(결정 기록 — 확정된 해석·방침)와 GLOSSARY.md.
여기 적힌 확정 해석("AA 이상"=문자 그대로, 위험등급 1=매우 위험, 값 0인 행은 목록에서
제외, 매수가능=만기 도래 제외 전부 등)과 어긋나는 수정은 금지다.

수정 원칙 (전부 지켜야 한다):
1. 일반 정책만 — 특정 문항의 문장·상품명을 하드코딩하는 규칙 금지. "처음 보는 비슷한
   질문에도 도움이 되는가?"를 스스로 물어볼 것.
2. 수정마다 시험을 함께 — tests/ 아래에 같은 뜻 다른 표현 2~3개짜리 시험을 추가한다
   (tests/test_v2_fixes.py 의 스타일 참고).
3. 애매한 해석은 답변에 명시 — 해석이 갈리는 표현을 처리할 때는 채택한 해석을
   답변 노트(plan.notes)로 남긴다.
4. 결정성 유지 — 같은 질문이면 항상 같은 답이 나와야 한다. 무작위성·시간 의존 금지.
5. 거절 비대칭 — "없다는 적극적 증거"가 있을 때만 거절. 애매하면 한계를 밝히고 답한다.
6. 주최 데이터 우선 — 외부 지식·AI 사전지식으로 데이터에 없는 사실을 답에 넣지 않는다.

고치는 곳(대부분 이 넷 중 하나):
- engine/router.py — 질문을 어느 조회로 보낼지 정하는 규칙 (새 질문 유형 대응은 주로 여기)
- engine/sql_templates.py — 미리 검증된 SQL 조회문 목록 (새 정렬·필터·결합이 필요할 때)
- kg/build_kg.py + ontology/ — 지식그래프에 넣을 관계·속성 (새 '관계' 질문 대응)
- engine/answer_service.py / validation.py — 답변에 붙는 사실 노트·검문(거절 판정)

수정 후 반드시(순서대로):
1. python -m pytest tests/ -q   → 전부 통과할 때까지
2. 내 세트 재채점(HCX 포함):
   python evalset/eval_runner.py --evalset evalset/evalset_<이름>.jsonl --checks evalset/checks_<이름>.jsonl --tag blind_<이름>_fixed
   (수정을 반복하는 중간에만 --no-hcx 로 빠르게 확인해도 된다. 단 "고쳐졌다"는 최종 판정은
   반드시 HCX 포함 결과로 한다 — 실전 구성이 기준이기 때문이다.)
3. 관련 문항 표적 확인(선택) — 내 수정이 건드린 규칙과 직접 관련된 기존 문항이 있으면
   그 문항만 골라 확인한다(전체 재채점 금지 — 8/28 저녁 확정):
   python evalset/eval_runner.py --evalset evalset/evalset_v1.jsonl --checks evalset/checks_v1.jsonl --ids "L-01,L-02" --tag touch_<이름>
4. 재채점에서 새 실패가 나오면 그것도 고친다 — "수정 직후 재채점"이 우리 절차다.

끝나면:
- evalset/EVALSET_README.md §11 의 내 바퀴 절에 "개선 결과"를 추가: 무엇을 왜 고쳤나(파일·규칙 이름),
  점수 변화(전→후), 표적 확인한 기존 문항 결과, 추가한 시험 목록.
- 커밋·푸시(main 직접): git pull 먼저 → 위 1~3이 전부 통과한 상태인지 확인 →
  git add(단, .env·krx_cookie.txt·API 키가 diff에 없는지 확인) → 한글 커밋 메시지
  ("무엇을·왜"가 보이게) → git push origin main. --force 금지.
```

## 6. [4단계] 올리고 알리기

- main 푸시가 끝나면 팀 채널에 **3줄 보고**: ① 내 세트 점수 전→후 ② 고친 것 한 줄씩
  ③ 표적 확인한 기존 문항 결과(있으면).
- 리더는 보고를 보고 시험 전부 통과·이상 없는 커밋에 `stable-날짜` 태그를 남긴다(안전지점).
- 문제가 생기면(점수 하락 발견) 리더가 마지막 stable 태그 기준으로 원인 커밋을 찾아 되돌린다 —
  본인이 직접 되돌리지 말고 리더에게 알린다.

## 7. 자주 나오는 질문

- **채점기가 뭘 보나?** 4가지 축 — ① 태도(답해야 할 문항에 답했나, 거절해야 할 문항에
  거절했나) ② 근거 표시(출처·기준일) ③ 내용(검사표와 대조 — 기대 이름·숫자·해석 문구)
  ④ 응답 시간. 종합 통과 = ①+②+③ 전부 통과.
- **왜 내 문항은 HCX 포함이 기준인가?** 실제 주최 평가가 HCX 포함 실전 구성이기 때문.
  HCX를 빼면 생성 문장·AI 경로가 빠져서 점수가 실전과 달라진다.
- **통과한 문항을 왜 다시 안 보나?** 한 번 통과한 문항의 반복 재채점은 시간 대비 소득이
  작다(8/28 저녁 사용자 확정 — 그 시간에 새 문제를 만드는 게 성능을 더 올린다). 하락이
  의심되면 그 문항만 표적 재채점, 확인되면 stable 태그 기준으로 리더가 되돌린다.
  데이터 전면 교체급 변화 때만 전체 재채점(사용자 승인).
- **내 문항이 기존 세트와 겹치면?** 괜찮다. 다만 세트 파일 이름은 겹치지 않게
  `evalset_<본인이름>.jsonl` 로만 만든다(v1/v2/v3/mirror 파일은 건드리지 않는다).
- **데이터가 어느 판인지 헷갈린다** — 8/26 재배포본(파일명 `prbd01n001_data.xlsx` 식 소문자)이
  맞다. 07/11 구본(`*_20260711_datarows.xlsx`)으로 재구축하면 행수 검증에서 바로 멈추게 되어 있다.
- **AI가 코드가 아니라 문서만 보고 답하게 하고 싶다** — 1단계에서는 저장소 밖(일반 챗)에서
  작업하면 자연스럽게 지켜진다.
- **두 명이 동시에 푸시하다 충돌하면?** 푸시 직전 `git pull`이 규칙인 이유다. 충돌이 나면
  AI에게 "충돌을 해결해 달라"고 하고, 해결 후 시험·회귀를 다시 통과시킨 뒤 푸시한다.
