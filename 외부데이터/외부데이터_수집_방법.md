## 1. 한눈에 보기 (핵심)

**무엇을 수집했나:** 시세·수익률 같은 "값"이 아니라, 제공 데이터를 해석하는 **메타데이터**(컬럼 사전·값 사전·별칭 사전·등급 서열표·코드표·지수 정규화 사전)를 수집했다. 총 428건, 전 항목 출처 표기, 오류 위험이 큰 3개 영역은 교차 검증으로 13건 정정.

**왜 값이 아니라 해석인가:** 대회 규칙상 채점 정답지는 제공 데이터(2026-07-11 스냅샷)로 만들어진다. 외부에서 가져온 값은 정답을 맞게 만들 수 없고 **틀리게만 만들 수 있다** (출제진이 "확인할 수 없음"을 기대하는 결측 질의에 외부 값으로 답하면 감점). 반면 해석 메타데이터는 리스크 없이 정확도를 올린다 — semantic layer 연구 기준 컬럼 정의·값 매핑·동의어 유무가 정확도 +17~23%p를 가른다(Cube 벤치마크, BIRD external knowledge +20%p).

**3-Tier 수집 원칙**

| Tier | 대상 | 방침 | 상태 |
|---|---|---|---|
| 1 — 적극 수집 | 해석 메타데이터 (용어·등급·코드·별칭·지수) | 좁고 깊게, 전 항목 출처 필수 | ✅ **완료 (이 문서)** |
| 2 — 조건부 | 결측 필드 보강 (펀드 보수 등) | 8/6 예시 질의 확인 후 "출처 명시 부가정보"로만 | 보류 |
| 3 — 금지 | 시세·수익률 시계열 대체 | 스냅샷과 반드시 상충 → 사용 금지 | — |

## 2. 왜 이 데이터들을 수집했는가

제공 데이터의 해석 난이도가 상품군마다 극단적으로 다르다:

- **국내채권(42,394건)**: 스키마에 한글 컬럼명이 **하나도 없다**. `DUR`, `COV`, `DIRTY`, `NDY_APPLIED_YIELD`, `DEPO_EQUIV_YIELD_154` 같은 약어 40개를 해석하지 못하면 테이블 전체를 못 쓴다.
- **해외ETF(5,646건)**: 한글명 없음 + 기초지수가 Lipper 영문 표기(수익률 유형 접미어 TR/PR/NR/CR 포함).
- **사용자 질의는 데이터의 언어로 오지 않는다**: "타이거 미국S&P500"(브랜드 별칭), "곱버스"(은어), "AA급 이상"(등급 표현), "KBSTAR ETF"(2024년에 RISE로 리브랜딩된 구명). 별칭·정규화 사전 없이는 조건 추출이 불가능하다.
- **등급·코드는 서열과 체계가 필요하다**: "신용등급 AA 이상" 필터는 등급 서열표(AAA=1~D=20)가 있어야 SQL이 된다. 위험등급은 법적 체계가 2개 병존(2016 금감원 표준편차 기준 / 2023 금소법 VaR 기준)하지만 등급 명칭이 같아 1~6 매핑으로 통일 가능함을 확인했다.

즉 수집 대상 선정 기준은 단순하다: **"이게 없으면 어떤 질의가 틀리는가?"** 각 사전은 특정 질의 유형의 실패 모드에 대응한다.

## 3. 어떻게 수집했는가

### 3-1. 파이프라인 (3단계)

```
① 실측 (내부)          ② 웹 리서치 (외부)         ③ 적대적 검증
xlsx 4쌍 전수 스캔   →   8개 도메인 병렬 리서치   →   오류 위험 상위 3개 도메인
- 207개 컬럼 스키마      - 에이전트 8개 병렬          (채권약어·신용등급·별칭)
- 범주형 고유값 423행    - 전 항목 출처 URL 필수      - 반박 시도 → 13건 정정
- 브랜드 접두어/지수명   - 확인 불가 시 low 표기      - 106건 검증 통과
```

핵심은 **①이 ②를 결정한다**는 것: 웹에서 막연히 "채권 용어"를 검색한 게 아니라, 데이터에 실제로 존재하는 값(예: `CRD_GRD`의 'AA0', BD_KND의 'Conduit회사채', 브랜드 접두어 'N2', '1Q')을 추출해 그것만 조사했다. 그래서 사전의 모든 항목이 데이터의 실제 값과 1:1로 연결된다.

### 3-2. 어디서 수집했는가 (출처 정책)

공식/1차 출처 우선: 금융투자협회(KOFIA)·KRX·금융감독원·금융위원회 규정, 신용평가 3사 등급정의 원문, 각 운용사 공식 사이트, ISO 표준, 증권사 채권 화면(용어 각주), 리브랜딩 보도. **웹에서 확인 못 한 추정은 `confidence=low`로 정직하게 표기**하고 8/6 설명회 질문 목록으로 넘겼다 — 그럴듯한 추정을 high로 위장하는 것이 사전의 최악 오염이기 때문이다.

### 3-3. 검증(정정 13건)의 예

- `EVAL_PRICE` 설명의 "민평 4사"는 부정확 → 금투협 등재 채권평가사는 5개사(관행상 4사 평균 사용)로 정정
- SOL 리브랜딩 "2021년 9월" → **2021년 8월**로 정정 (KRX 공시일 기준)
- `NDY_*` = "익일(Next Day)" 해석은 웹 근거가 없어 **추정 등급으로 하향** (민평 데이터의 발표일/적용일 관행이 정황 근거)

## 6. 어떻게 활용하는가

1. **조건 추출/정규화**: 사용자 질의의 "타이거"·"곱버스"·"AA급"을 별칭사전·등급사전으로 표준 코드로 변환 → SQL 파라미터. 런타임 LLM 추측 대신 사전 조회(결정적).
2. **taxonomy_mapping seed**: 팀 가이드(main 브랜치 `PROJECT_GUIDE.md`)의 수동 매핑 테이블(지역·자산군) 초안 재료로 값사전·코드표를 사용.
3. **커버리지 판정**: 센티널 목록(코드표·기초지수 사전)이 "확인할 수 없음" 판정의 근거.
4. **think_trace 근거 표기**: 답변에 사용한 해석(예: "AA0은 AA로 해석")의 출처를 사전에서 인용 가능 — 정성평가 '리스크 관리' 대응.
